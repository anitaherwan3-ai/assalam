**Method:** Static source inspection of `js/store.js` and `js/firebase-backend.js`; no live Firebase export or database query.

## 1. Executive decision

**Migration data readiness: NOT VERIFIED; bulk import is blocked.**

The source reveals 16 application data collections in the local store, three additional Firestore namespaces used directly by the backend/configuration, and an auxiliary return-quota collection. Document IDs are heterogeneous and frequently act as business references. Firestore snapshots overwrite/merge `id` from the document path, so the document path—not a possibly stale embedded `id`—must be retained as the authoritative legacy document identifier.

No live documents were read. Consequently, this audit does **not** assert that duplicates, orphans, malformed timestamps, or missing fields exist (or do not exist). Those require a read-only export/profile of the actual Firebase dataset.

## 3. Document IDs and source identity

Observed patterns include:
- Patient/queue: deterministic `q_YYYYMMDD_NNNNNN`; legacy rows may have other IDs and must not be rewritten.
- Medicine/batch/tariff/package examples in local seed: short IDs such as `o1`, `b1`, `t1`, `p1`.
- Return quota: derived key `<trxId>__<itemIndex>`.
- Cancellation request: document ID equals invoice ID.
- Invoice, shift, petty cash, purchase, return and audit IDs are generated by application helpers or workflow code; the source must be preserved exactly.
- User profiles are keyed by profile identity/email in current code, while Firebase Auth uses UID. The mapping must be explicitly exported and verified.

**Required migration identity key:** `(source_system, source_collection, source_document_id)`. Preserve exact source document path and raw document ID in a migration crosswalk. Do not impose a global UNIQUE constraint on raw IDs across collections. Keep a separate immutable `legacy_document_id`/crosswalk and a deterministic target primary key.

Firestore snapshot code maps `doc.data()` then assigns `id: doc.id`; this confirms the path ID is the effective source identity in the current listener. Import must also preserve the original embedded `id` as raw payload metadata if it differs, so discrepancies are auditable.

## 4. Duplicate and orphan checks — required but not executed

No historical data was read, so there are no live duplicate/orphan counts. The import profiler must produce exception reports before any insert:

1. Duplicate document paths (should be impossible within one collection, but verify export integrity); duplicate embedded IDs that differ from document IDs.
2. Duplicate business identifiers: invoice numbers, batch numbers within medicine/supplier context, queue number by clinic business date and queue type, active cashier shift, and quota key.
3. Orphan invoices: missing patient/encounter, shift, cashier/user, or invoice-line medicine/batch allocation.
4. Orphan return/cancellation records: missing invoice, invalid item index, over-return, inconsistent reserved/used quota, or stock restoration without an approved source event.
5. Orphan batches and movements: missing medicine, purchase/receipt, invoice allocation, return/cancellation or loss source.
6. Supplier chain: purchase ↔ supplier ↔ batch ↔ supplier return ↔ payment/credit.
7. User/profile/Auth: profile without Auth UID, UID mapped to multiple profiles, email mismatch, inactive profile, role mismatch.
8. Referential and aggregate reconciliation: invoice item totals, stock and batch balances, return totals, shift cash, supplier balance and financial report totals.

Do not silently discard, merge, or fabricate parents for exceptions. Quarantine unresolved records with source path, raw JSON, reason code and owner resolution status.

## 5. Timestamp and date normalization

Source uses multiple representations:
- `_t`, `updatedAt`, approval/payment/cancellation timestamps are generally JavaScript epoch milliseconds (`Date.now()`).
- Business dates such as `tgl`, expiry `ed`, and purchase/payment dates are date-only strings.
- Several writers use `new Date().toISOString().slice(0, 10)` (UTC date), while clinic reporting and current-day logic use `Asia/Jakarta`.
- Local device clock/time and UTC-derived date are mixed; missing/invalid timestamps can exist in legacy rows and cannot be normalized by assumption.

**Import rule:** retain raw timestamp value and source field; classify field semantics before conversion. Convert known epoch-millisecond instants to UTC DATETIME(3) (or an explicitly selected instant representation), and separately derive Asia/Jakarta business date where business rules require it. Date-only values remain DATE. Do not treat date-only values as UTC midnight, do not multiply epoch milliseconds twice, and do not replace unknown/malformed values with current time.

Required profiler output: field path, observed JSON type, null/missing count, min/max, invalid count, epoch seconds vs milliseconds candidate count, date-string format distribution, and timezone conversion exceptions.

## 6. Null/missing and shape profiling

Firestore is schemaless. Source code often defaults missing numeric values to zero and missing arrays to empty arrays, but migration must not erase the distinction between:
- field absent,
- explicit `null`,
- empty string,
- numeric zero,
- empty array/object,
- malformed value.

Preserve raw source JSON and record normalized value plus a conversion status. Do not fill unknown actor, cashier, patient, batch, date, amount, approval or payment fields with invented values. Required-vs-optional decisions must follow the approved domain contract and source evidence.

## 7. Ownership chains and migration reconciliation

The following are mandatory cross-collection reconciliation groups:

- `pasien → trx → shift → users`: legacy patient rows are encounters/queue rows; preserve exact queue ID and invoice-time patient snapshot. Validate invoice patient reference, cashier, and shift ownership.
- `trx.items → obat → batch`: preserve invoice line index, medicine and batch allocation snapshots, quantities, sale price and HPP; totals must reconcile to invoice.
- `trx → returJual → returKuota`: quota is per invoice item index; reconcile requested, reserved, rejected/released, approved and paid quantities/amounts. Service returns and package components require their own correct line identity.
- `trx → batalTrx`: one cancellation workflow per invoice; verify approved status and exactly-once stock restoration.
- `beli → batch → returBeli → supplier/payment`: retain supplier and batch lineage, payment status and any supplier credit/return.
- `shift → petty/log`: preserve cashier ownership, shift boundaries, opening float, physical count, variance and verification events.
- `users ↔ Firebase Auth`: map all five owner-protected accounts by UID, email, profile key, active state and role; no account/profile mutation during migration readiness work.

Reconcile both row counts and financial/inventory aggregates per source collection and business date. A successful insert count alone is not proof of correctness.

## 9. Staged migration protocol

1. Freeze a versioned, read-only Firebase export including all discovered collections, Auth UID/profile crosswalk, document paths, raw JSON and export timestamp. Protect credentials and personal data.
2. Generate collection inventory and deterministic source hash per document; record export manifest and counts.
3. Run the profiler and duplicate/orphan/shape/date checks without writing to TiDB.
4. Resolve or quarantine exceptions; no silent merge. Patient identity resolution remains suggestion-only and must not auto-merge by name/phone.
5. Import to isolated staging tables with source-scoped idempotency key and raw payload retention.
6. Normalize into domain tables only after source-to-target mapping is approved; preserve legacy IDs and snapshots.
7. Reconcile counts, amounts, stock/batches, quota, shift cash and supplier balances; rerun import to prove idempotency.
8. Test restore from export and TiDB backup before any cutover decision.
9. Keep Firebase intact as rollback/archive until explicit cutover acceptance.

## 10. Exit criteria and test plan

Schema v1/data import remains blocked until:
- complete source export manifest and actual collection counts are available;
- all five protected accounts are read-only verified against Auth UID and profile/role;
- duplicate/orphan/missing/null/date reports are produced from actual export;
- source-scoped ID crosswalk and raw-payload retention are implemented;
- patient/encounter/invoice/shift/cashier and medicine/batch/return ownership exceptions are resolved or quarantined;
- count and monetary/stock reconciliation reaches exact expected totals, with documented rounding rules;
- repeated dry-run import is idempotent;
- backup restore and rollback are proven.

Suggested synthetic tests (not executed): same raw ID in two collections; embedded ID differs from path; duplicate invoice number; missing encounter; invoice with wrong shift cashier; return item index out of range; quota greater than sold quantity; approved return without stock event; timestamp seconds vs milliseconds; UTC midnight crossing WIB date; null vs missing vs zero; malformed date; missing user UID; stale profile email; repeated import; partial import retry.
